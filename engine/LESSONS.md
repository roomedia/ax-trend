# LESSONS — 실운영 실패 교훈

이 엔진의 규칙은 대부분 실패에서 나왔다. 날짜는 교훈이 확정된 시점.

## 1. 원문 날짜를 직접 확인해라 (2026-10-09)

검색 스니펫의 날짜를 믿고 2026-06-08 기사를 10월 기사로 착각해 발행했다 (#3123).
이후 규칙: **원문 페이지의 `datePublished`/기사입력일을 직접 열어 확인**하고,
`freshness_hours`를 초과하면 발행하지 않는다. 의심스러우면 탈락.

## 2. 멀티워드 1회 검색은 실패 패턴이다 (2026-10-06)

`gh search issues "Reflection Beam"`은 0건을 반환했지만,
단독 토큰 "Beam" 검색으로는 중복 이슈 #3021을 바로 찾았다.
이후 규칙: 후보 엔터티를 **단일 토큰으로 분해**해 각각 검색한다.
회사명/제품명/모델명/주제 키워드를 한 번에 묶어 검색하지 않는다.

## 3. 검색 인덱스는 늦는다 (2026-10-06)

신규 이슈는 `gh search issues` 인덱스에 늦게 반영된다.
이후 규칙: 발행 직전 **최근 open 100건 제목을 직접 스캔**한다.
`fingerprint.sh`가 이 역할을 한다.

## 4. 닫힌 이슈도 중복이다 (2026-10-06)

`gh search issues`는 상태 필터를 주지 않으면 open/closed 모두 반환한다.
닫힌 이슈(#3021처럼)도 같은 사건이면 중복으로 제외한다.

## 5. 과요약 금지 (2026-10-06)

초기 이슈는 3~5줄 요약이었다. 읽고 나면 원문을 다시 찾아야 해서 쓸모가 없었다.
이후 규칙: 300~450단어 다이제스트 — 핵심 사실 5~8불릿 + 배경 + 미확인 사항 + 실무 함의 + 원문 링크.
**이 이슈만 읽고도 내용을 파악할 수 있어야 한다.**

## 6. 라벨 없이 발행 (운영 정책)

이슈 생성 시 라벨을 붙이지 않는다. 분류는 제목·본문·핑거프린트로 충분하고,
라벨은 나중에 정리할 때 붙이는 게 낫다.

## 7. 애매하면 합쳐라 (2026-10-11, AIHOT에서 차용)

"같은 사건인지 후속인지 애매하다" = 중복으로 처리한다.
발행은 되돌릴 수 있지만(닫으면 됨), 빠진 사건은 아무도 모른다 — 가 아니다.
반대다: **중복 발행은 다이제스트의 신뢰를 깎고, 빠진 사건은 다음 사이클이 잡는다.**
의심스러울수록 발행하지 않는 쪽.

## 8. X·Threads 게시물도 출처다 (2026-10-11)

공식 계정의 론칭·발표 게시물은 뉴스보다 빠르다 (#3209 promptwhat.net 론칭이 X 게시물로 확인됨).
공개 게시물은 라이브 브라우저로 로그인 없이 읽을 수 있다.

## 9. 수치·날짜·인용은 원문에서 그대로 찾아라 (2026-10-15, imozuru에서 차용)

이슈 본문의 수치·날짜·인명·제품명·금액·인용은 원문 텍스트에서 그대로(verbatim) 발견되어야 한다.
핵심 사실 불릿마다 원문 내 근거를 대조하고, 못 찾은 주장은 삭제하거나 "미확인"으로 표기한다.

## 10. 확인할 주장을 먼저 3가지로 정해라 (2026-10-15, imozuru에서 차용)

후보마다 발행 전 확인할 주장 — ① 원문 게시일 신선도 이내 ② 핵심 사실의 1차 소스 근거 ③ 신규성.
3가지 모두 증거가 붙으면 평가를 종료하고, 하나라도 없으면 탈락 또는 보류한다.

## 11. 뉴스보다 용어를 먼저 잡아라 (2026-10-16, new-term-radar에서 차용)

신규 AI 용어는 "X 발표 → GitHub 폭발 → 디렉터리·도메인 등록 → Google Trends 반영" 순서로 흔적을 남긴다.
키워드 도구는 마지막 단계만 읽으므로 2주 늦다. X·GitHub·HF에서 신규 고유명사를 먼저 포착하고,
급성장 정량 기준(14일 내 생성 + 일평균 200스타 이상 또는 전일 대비 +400)으로 우선순위를 정한다.
단순 리포스트·인용은 제외하고 원 게시물만 본다. 작성 시각을 신선도 기준일로 사용하고,
공식 계정 발표는 T1.5 등급을 적용한다.

## 12. 제목의 `$`는 셸이 먹는다 (2026-11-13)

`gh issue create --title "월 $20부터 ..."`처럼 제목을 큰따옴표 안에 인라인하면
`$2`·`$0`이 셸 위치 인자로 확장된다. #3968 제목이 "월 0부터"($2 → 빈 값),
#3967 제목이 "건당 /bin/bash.005"($0 → /bin/bash)로 발행됐다.
본문은 `--body-file`이라 멀쩡했다 — 깨진 건 제목뿐이었다.
이후 규칙: 제목·본문 모두 파일로 쓰고 `scripts/create-issue.sh`로 발행한다.
히어독은 `<<'TITLE'`처럼 인용해 열고, 제목을 명령줄에 직접 쓰지 않는다.

## 13. 워크플로 안에 파이썬을 인라인하지 마라 (2026-11-14)

`unicode-fixer-ci`는 셸 큰따옴표 안에 파이썬을 넣은 탓에 매 실행 SyntaxError로 죽었다 —
`'\u'` 리터럴이 잘린 이스케이프로 파싱됐다. 남아 있는 실행 기록 100건(2026-11-09~11-14)이 전부 failure였고,
그 사이 이슈 편집은 반영된 적이 없다.
같은 코드에 `encode('utf-8').decode('unicode-escape')`가 있어서, 실행됐더라도 한글을 모지바케로
망가뜨렸을 것이다(그 함수는 ASCII가 아닌 바이트를 전부 이스케이프로 해석한다). 그리고 `shell=True` +
f-string 조립은 #3967·#3968과 같은 `$` 확장을 한 번 더 일으킬 자리였다.
이후 규칙: 워크플로는 `.github/scripts/*.py`를 파일로 호출한다. `gh`는 `subprocess` argv로,
본문·제목이 길면 `gh api --input <json 파일>`로 넘긴다. 셸 문자열 조립은 하지 않는다.
