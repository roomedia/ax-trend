# RUNBOOK — 한 사이클 실행 절차

이 문서를 에이전트에게 그대로 전달하면 한 사이클이 실행됩니다.
설정값은 `config.yaml`을 따릅니다.

## 0. 준비

- `config.yaml` 읽기: `repo`, `timezone`, `reader`, `sources`, `thresholds`, `lanes`, `freshness_hours`.
- `prompts/`의 세 프롬프트를 읽는다: `selection-score.md`, `event-clustering.md`, `issue-format.md`.
- GitHub 인증 확인: `gh auth status`. `repo` 스코프 필요.
- **GitHub 작업은 `gh` CLI만 사용한다.** MCP·웹 UI 경로는 쓰지 않는다.

## 1. 수집 (collect)

1. `config.yaml`의 `topics`를 기준으로 최근 `window_hours` 내 뉴스를 웹 검색한다.
   주제 예: 인기 스킬/플러그인, AI 업계 소식, 새로운 패러다임, 모델 릴리스, AI 코딩·에이전트 도구, 온디바이스 AI, 한국 AI 업계.
2. **소셜 게시물도 출처에 포함한다.** X·Threads 공개 게시물은 라이브 브라우저로 로그인 없이 읽을 수 있다 (2026-10-11 검증).
   공식 계정의 론칭·발표·출시·주요 업데이트 게시물은 T1.5 등급 소스로 취급한다. 단순 리포스트·인용은 제외하고 원 게시물만 본다.
   게시물의 작성 시각을 신선도 기준일로 사용한다.
   `config.yaml`의 `follow_accounts`에 등록된 계정의 최근 게시물을 우선 탐색 대상으로 삼는다.
3. GitHub 트렌딩도 스캔한다 (일간·주간): AI/에이전트/모델/코딩 도구 관련 레포 중
   최근 30일 생성·급성장 또는 주간 상위 진입작. 단순 튜토리얼·포트폴리오·리스트 모음은 제외.
   **급성장 정량 기준** (new-term-radar에서 차용): `gh search repos --created ">=14일 전" --sort stars`로
   후보를 뽑고, (현재 스타 ÷ 생성 후 경과일) ≥ 200 또는 최근 24시간 +400 이상인 레포를 '급성장'으로 우선한다.
   '하루 800스타 레포 1개 = 전부인 시그널' — 단일 폭발 시그널도 후보로 삼는다.
4. Hugging Face 트렌딩도 스캔한다 (무료 API): 최근 트렌딩 상위 신규 모델을 AI 모델 클러스터 후보로 삼는다.
5. **용어 선행 포착** (new-term-radar에서 차용): 뉴스보다 먼저, X·GitHub에서 처음 보는 고유명사(모델명·제품명·레포명)가
   2개 이상 독립 소스에서 등장하면 후보로 승격한다. prioritize/watch/skip 판정을 채점 전 1차 필터로 쓴다.
6. 제외: `config.yaml`의 `exclude` (기본: 정치·정부 정책 뉴스), 라운드업·회고·재탕, 보도자료 재배포.

## 2. 채점 (score)

1. `prompts/selection-score.md`를 읽고 후보마다 **독립 2회** 0~100점 채점.
2. 두 회차 합 ≥ `2 × 임계값`인 것만 통과. 임계값은 소스 등급별 (`config.yaml`의 `thresholds`):
   T1(공식 1차)=60, T1.5=65, T2(미디어·개인·재배포)=76.
3. 채점 전 자동 탈락: 원문 `datePublished`/기사입력일이 `freshness_hours`(기본 48) 초과 —
   **검색 스니펫 날짜가 아니라 원문 페이지를 직접 열어 확인한다.** 의심스러우면 탈락.

## 3. 군집 = 중복 제거 (cluster)

**3-1. 핑거프린트 대조 (발행 직전 read)**
1. `scripts/fingerprint.sh <owner/repo>` 실행 → 최근 open 100건의 `제목 | 핑거프린트` 목록.
2. 후보의 핵심 엔터티를 **단일 토큰으로 분해** (회사명/제품명/모델명/키워드 각각).
   예: "Reflection Beam" → "Reflection", "Beam" 각각 대조. 멀티워드 1회 검색은 실패 패턴.
3. 영어·한글 표기 각각 대조. 버전 숫자 차이·번역 차이는 무시하고 엔터티 기준 판정.
4. 추가로 `gh search issues --repo <repo> <토큰>`으로 open+closed 전수 확인 (검색 인덱스 지연에 유의).

**3-2. 이벤트 군집 판정**
1. 3-1 통과 후보에 대해 `prompts/event-clustering.md`로 모델 판정:
   **같은 사건** (발행 금지) / **후속** (새로운 사실 있으면 발행) / **별개** (발행).
2. 애매하면 합친다. 의심스러울수록 발행하지 않는 쪽.

## 4. 발행 (publish)

1. `prompts/issue-format.md` 형식으로 이슈 생성. 제목: 한국어, 핵심 엔터티 + 사건 + 날짜/출처.
2. **발췌 검증** (imozuru에서 차용): 본문의 모든 수치·날짜·인명·제품명·금액·인용은 원문 텍스트에서
   그대로(verbatim) 발견되어야 한다. 핵심 사실 불릿마다 원문 내 근거를 대조하고, 원문에서 못 찾은 주장은
   삭제하거나 "미확인"으로 표기한다. 날짜·가격·스펙처럼 액션 가능한 수치는 특히 엄격히 대조한다.
3. **확인 주장 3선** (imozuru에서 차용): 후보마다 발행 전 확인할 주장 3가지를 먼저 정한다 —
   ① 원문 게시일 `freshness_hours` 이내(원문 `datePublished` 직접 확인) ② 핵심 사실의 1차 소스 근거
   ③ 신규성(중복 아님). 3가지 모두 증거가 붙으면 평가를 종료하고, 하나라도 없으면 탈락 또는 보류한다.
4. 본문 끝에 핑거프린트 삽입 (멀티 에이전트 중복 방지):
   ```html
   <!-- ax-events: 토큰1,토큰2,한글토큰 -->
   ```
   토큰 규칙: 소문자 영문 + 한글 원형, 공백·특수문자 제거, 엔터티당 1토큰.
3. `gh issue create --repo <repo> --title "..." --body-file ...` 로 생성. `--label`은 붙이지 않는다 (운영 정책에 따름).
4. 생성 직후 URL을 기록한다.

## 5. 보고 (report)

- 새 이슈가 있을 때만 다이제스트 전달 (형식: `**#번호** — 제목` + 이슈 URL). 없으면 조용히 종료.
- 새 이슈가 3건 이상이면 채점 점수 상위순으로 배열.

## 멀티 에이전트 운영 규칙

- 동시에 도는 에이전트는 `config.yaml`의 `lanes`에서 서로 다른 레인을 맡는다.
- 발행 직전(3-1)은 **반드시** 실행한다 — 다른 에이전트가 조금 전에 발행한 이슈를 잡는 유일한 방법.
- 그래도 중복이 생기면 레포의 `deduplicate-issues` Action이 정리한다. 걱정 말고 발행해라.
